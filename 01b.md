# 12 — llama.cpp + GGUF compilé à la main : étape par étape

La version concise pour la **méthode avancée** : compiler `llama.cpp` toi-même au lieu d'utiliser Ollama. Pas de blabla, juste les commandes.

> **Lis avant** : [`docs/11-ollama-quickstart-etape-par-etape.md`](./11-ollama-quickstart-etape-par-etape.md). Si Ollama te suffit, reste sur Ollama. Cette méthode est pour ceux qui veulent compiler eux-mêmes.

---

## D'abord : c'est quoi CMake et pourquoi compiler ?

**CMake** = un outil qui génère des fichiers de build (Makefiles, projets Visual Studio…) à partir d'un fichier `CMakeLists.txt`. Il **ne compile pas lui-même**, il prépare le terrain pour MSVC, GCC ou Clang qui font le vrai boulot.

```
CMakeLists.txt  →  CMake (génère)  →  Visual Studio project / Makefile  →  MSVC compile  →  llama-server.exe
```

**Pourquoi compiler `llama.cpp` toi-même** au lieu d'utiliser Ollama ?

| Raison | Explication |
|--------|-------------|
| Optimisations CUDA spécifiques | Compile pour **ton** GPU exact (sm_89 RTX 40xx, sm_120 RTX 50xx) |
| Versions très récentes | Toujours la dernière nightly de `llama.cpp` (Ollama est 1-3 mois en retard) |
| Flags expérimentaux | Speculative decoding, KV cache quantification, multi-GPU fin… |
| Pas de surcouche | Tu lances `llama-server.exe` directement, pas de service en arrière-plan |
| Apprentissage | Tu comprends la stack de bout en bout |

**Inconvénient** : 5 à 15 min de compilation et plein de pièges Windows. Si tu n'as pas de besoin pointu, **utilise Ollama** (doc 11).

## Étape 4 — Compiler avec CMake + CUDA (5–15 min)

C'est l'étape critique. Le script gère **tous** les pièges Windows pour toi.

```powershell
.\scripts\03-build-llama.ps1
```

### Ce que le script fait en arrière-plan

1. Charge l'environnement MSVC (`vcvars64.bat`)
2. Force le CMake **3.29 de Visual Studio** (pas le standalone qui plante)
3. Tue les processus zombies du build précédent
4. Supprime `llama.cpp\build` (avec retry)
5. Lance `cmake -B build -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release`
6. Lance `cmake --build build --config Release -j --target llama-server`
7. Vérifie la présence de `llama.cpp\build\bin\Release\llama-server.exe`

### Sortie attendue à la fin

```
=== BUILD OK ===
Name          : llama-server.exe
Length        : 8660992
LastWriteTime : ...
```

### Si ça plante

Ne panique pas — voir la section [Erreurs fréquentes](#erreurs-fréquentes) en bas.

## Étape 5 — Setup Python + Hugging Face

```powershell
.\scripts\04-setup-python-hf.ps1
```

Ça crée le venv `.venv`, installe `huggingface_hub`, et lance `hf auth login`.

### Pendant le login

1. Va sur [huggingface.co/settings/tokens](https://huggingface.co/settings/tokens)
2. **New token** → **Read** → **Generate** → copie le `hf_xxx`
3. **Clic droit** dans le terminal pour coller (rien ne s'affiche, normal)
4. **Entrée**
5. À `Add token as git credential? (Y/n)` → tape `n`

⚠️ Tu vas voir du **rouge** autour des messages de `hf` — c'est cosmétique (PowerShell 5.1 transforme stderr en faux warnings). Le script continue.

## Étape 6 — Télécharger le `.gguf`

### Quel script selon ta VRAM

| GPU VRAM | Script |
|----------|--------|
| 12 Go+ | `.\scripts\05-download-model.ps1` (Q8, ~8 Go) |
| 8 Go (RTX 4070 Laptop…) | `.\scripts\05b-download-model-q6.ps1` (Q6, ~6 Go) |
| 6 Go ou moins | Télécharger manuellement un Q5_K_M ou Q4_K_M |

### Lancer

```powershell
.\scripts\05b-download-model-q6.ps1
```

Durée : 5 à 15 min selon la connexion. Le `.gguf` atterrit dans `C:\models\gemma4-e4b\`.

### Si bloqué à 0 octet

Le backend `hf-xet` est buggy. Le script a déjà le fix (`HF_HUB_DISABLE_XET=1`). Si tu télécharges manuellement, ajoute :

```powershell
$env:HF_HUB_DISABLE_XET = "1"
```

## Erreurs fréquentes

Synthèse des 10 problèmes connus (détails complets dans [`04-guide-complet-troubleshooting.md`](./04-guide-complet-troubleshooting.md)).

| # | Erreur | Cause | Fix rapide |
|---|--------|-------|-----------|
| 1 | `No CMAKE_ASM_COMPILER could be found` | CMake 4.x standalone vs MASM | Le script `03` utilise déjà le CMake 3.29 de VS. Sinon : `& "C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin\cmake.exe"` |
| 2 | `CMakeRCInformation.cmake (rc.exe)` | `vcvars64.bat` pas chargé | Lance le script depuis Developer PowerShell ou utilise le script `03` |
| 3 | `La ligne entrée est trop longue` | PATH > 8191 caractères (vcvars relancé plusieurs fois) | **Ferme** ce terminal et **ouvre-en un neuf** |
| 4 | `NativeCommandError` sur `cmake.exe : CMAKE_BUILD_TYPE=Release` | PS 5.1 traite stderr comme erreur | Le script `03` utilise `Start-Process` qui contourne ça |
| 5 | `Remove-Item ... en cours d'utilisation` | Process zombies (cl.exe, MSBuild.exe) du build précédent | `.\scripts\00-clean-build.ps1` puis relance |
| 6 | `hf : To log in...` en rouge | Cosmétique PS 5.1 | Ignore le rouge, colle ton token et continue |
| 7 | Téléchargement HF bloqué à 0 octet | Backend `hf-xet` buggy | `$env:HF_HUB_DISABLE_XET = "1"` (déjà dans le script `05`) |
| 8 | OpenClaude `Input must be provided` | TTY non détecté | Lance `openclaude` directement dans ton shell, **pas depuis un script** |
| 9 | `couldn't bind HTTP server socket port 8090` | Port pris (souvent Java) | `Get-NetTCPConnection -LocalPort 8090 -State Listen` puis change le port dans `07` |
| 10 | `llama-server` crash silencieux | OOM VRAM (Q8 sur 8 Go par ex.) | Utilise `05b` (Q6) au lieu de `05` (Q8), ou réduis `-c 8192` à `-c 4096` |
